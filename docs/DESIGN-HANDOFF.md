# Design handoff — UI/UX state, findings, and backlog

> **Written:** 2026-07-16. **Audience:** the next agent or developer picking up UI work on this fork (Codex or otherwise), cold, with no memory of the session that produced it.
>
> **Scope of this document:** what the design context files are, what changed in the stylesheet layout, what a full UX critique found, and what to do next in what order. It does **not** duplicate [`docs/UX-SPEC.md`](UX-SPEC.md) (which owns the target IA, screens, states, and content rules) or [`docs/PLATFORM-ROADMAP.md`](PLATFORM-ROADMAP.md) (phase order and feasibility). Those remain canonical for *intent*. This document covers *current state vs. that intent*.

## 1. Start here

Read these three, in this order, before touching UI code:

| File | Owns | Read it for |
|---|---|---|
| [`PRODUCT.md`](../PRODUCT.md) (root) | Strategy | Register, users, purpose, brand voice, anti-references, the 6 design principles, the a11y bar |
| [`DESIGN.md`](../DESIGN.md) (root) | Visual system | Tokens (normative, in YAML frontmatter), color/type/elevation doctrine, component specs, Do's and Don'ts |
| [`docs/UX-SPEC.md`](UX-SPEC.md) | Target UX | The IA, screens, flows, states, and validation checklist this fork is building toward |

Two machine-readable sidecars support them:

- `.impeccable/design.json` — tonal ramps, shadow/motion/breakpoint tokens, and 9 drop-in component HTML/CSS snippets that DESIGN.md's frontmatter schema can't hold.
- `.impeccable/critique/2026-07-16T17-03-09Z__app-index-html.md` — the full critique this document summarizes, with persona red flags and minor observations. **Read it before starting any P0 below.**

The three key facts that constrain every UI decision here:

1. **Register is product.** Design serves the task. Earned familiarity beats novelty; the tool should disappear into the job.
2. **The bundle is served off controller flash on a LAN with no internet.** No web fonts, no raster assets, no off-origin requests, no new runtime dependency, no UI framework. This is not a preference — recommending React/Tailwind/a component library is a non-starter. Graphics are inline `currentColor` SVG or they don't exist.
3. **The user is a homeowner on an iPhone in direct sunlight at a valve box.** Not an expert, not a firmware reader. Contrast bar is *above* WCAG AA for sunlight; body text is Ink, never `--muted`.

## 2. What changed (2026-07-16)

### Design context established

`PRODUCT.md`, `DESIGN.md`, and `.impeccable/design.json` are new. `DESIGN.md` was generated by scanning the real stylesheet — every token in it was extracted from code, not invented. Register (`product`), personality (friendly/forgiving/homeowner-first), anti-references, and the sunlight contrast bar were confirmed by the project owner, not inferred.

### The design system moved out of the demo harness

**Before:** `app/main.ts` did `import "../demo/style.css"; // DRAFT: shares the demo's view styling for now`. Production CSS was built out of a test harness.

**After:**

```
www/src/ui/tokens.css   ← the :root contract + dark mode + responsive token steps (normative layer)
www/src/ui/system.css   ← @import "./tokens.css" + every rule the product renders
demo/style.css          ← @import "../www/src/ui/system.css" + demo-only chrome (.banner, .controls)
```

`app/main.ts` now imports `www/src/ui/system.css` directly. Demo and production share one system; the demo adds harness chrome on top and production never sees it.

**Why the split matters:** UX-SPEC §14 says "add a token only when it appears in at least two shipped components." That rule is only reviewable if tokens are a separate file — a 55-line diff instead of a 270-line one. `tokens.css` is the contract; `system.css` consumes it. Keep it that way.

**Found in the process:** `.banner` and `.controls` (the demo's mock-explainer and LAN/OTC toggle) had zero references in `www/src` and were shipping to production in `dist/assets/app.css`. They're now demo-local.

**Verified, not assumed:**

| Check | Result |
|---|---|
| `npx vite build app` | passes |
| `npx vite build demo` | passes |
| `npx vitest run` | 159/159 pass |
| Production CSS gzip | **3368 → 3319 bytes (−49)** — measured by stashing the change and rebuilding |
| Demo chrome in `dist/assets/app.css` | 0 occurrences |

That gzip number is the UX-SPEC §14 baseline ("measure the production Vite gzip baseline… a >10% unexplained regression fails CI"). **Current baseline: 3319 bytes gzipped for `dist/assets/app.css`.** Reproduce with `npx vite build app && gzip -c dist/assets/app.css | wc -c`.

### Environment gotchas you will hit

- **Install hooks are opt-in.** Repository `.npmrc` disables dependency install scripts. After `npm install` or `npm ci`, run `npm run deps:rebuild`; that executes only the reviewed `better-sqlite3`, `esbuild`, and optional macOS `fsevents` hooks. `vite` is declared directly.
- **`npm install` on Windows** rewrites `package-lock.json`, stripping `libc` fields from optional platform deps. Unrelated churn — revert it (`git checkout package-lock.json`) rather than committing it.

## 3. Critique findings — `app/index.html`, 19/40 (Poor)

Full report: `.impeccable/critique/2026-07-16T17-03-09Z__app-index-html.md`. Scored against Nielsen's 10 heuristics; two independent assessments (design review + deterministic detector) were run in isolation and synthesized. No browser automation was available, so findings are source- and detector-derived — **a live pass at 320px would add real render-time evidence and is worth doing.**

### The one-line verdict

**This is not AI slop, and that's not the problem.** Zero hits across every anti-pattern ban. The detector (`detect.mjs`) is clean at exit 0. The design system is genuinely mature — derived accent variants via `color-mix` so dark mode inherits from one redefinition; a 13px help glyph with a 44px hit area that doesn't consume 44px of layout.

**The design system is three phases ahead of the product it dresses.** The rain delay is a `window.prompt` that cancels itself on a typo. Half the heuristics measure *behavior over time* — freshness, verification, recovery, editing — and the app has almost none of it. This is a render layer ~90% finished on an interaction layer ~30% finished.

### Score breakdown

| # | Heuristic | Score | Key issue |
|---|---|---|---|
| 1 | Visibility of system status | 1 | No polling anywhere; `refresh()` runs once at mount |
| 2 | Match system / real world | 1 | `Firmware`/`Cloud (OTC)` on Home; `"Saved to the device via /cp"` in copy |
| 3 | User control and freedom | 2 | Confirms name no target, no consequence; native `confirm()` focuses OK |
| 4 | Consistency and standards | 2 | `.settings` forms and `window.prompt` coexist; no native time/date/dialog anywhere |
| 5 | Error prevention | 1 | Rain-delay typo cancels the delay; new programs default enabled |
| 6 | Recognition rather than recall | 2 | Program editor: ~27 controls, no review, no next-run preview |
| 7 | Flexibility and efficiency | 2 | No way to edit an existing program |
| 8 | Aesthetic and minimalist design | 3 | System is excellent; Home shows 9 equal-weight rows, 3 matter |
| 9 | Error recovery | 2 | `errorCard` hardcodes "Couldn't reach the controller" for every failure |
| 10 | Help and documentation | 3 | `helpTip` is genuinely to spec |

**Cognitive load: 6/8 failures — HIGH.**

## 4. Backlog, in order

Every claim below was verified in source. Line numbers are as of 2026-07-16.

### P0-1 — Every mutation claims success it never verified, and nothing refreshes

**Evidence.** `grep -rn "setInterval\|visibilitychange\|navigator.onLine" www/src` → **0 hits**. `host.ts` calls `void refresh()` once at mount; nothing re-fetches except after a write. `host.ts:112` — `await deps.api.submitProgram(...); msg = "Program created."` then `deps.toast(msg)`. The toast fires on HTTP resolve, before the refresh, with no comparison of the decoded result. Same shape in every `dispatch.ts` case: `"All stations stopped."` (`:27`), `"Rain delay set to Nh."` (`:38`).

**Why it's P0.** PRODUCT.md's founding line: *"no mutation ever claims success it did not verify."* Zero mutations verify. The whole UX-SPEC §10 state table and §11 freshness contract are unimplemented — no Stale, no Offline, no "Last updated", no write-disabling when unreachable. A homeowner taps Stop all with water running, gets "All stations stopped.", and sees an unchanged screen. A stale Home reading `Controller: Enabled` from ten minutes ago is exactly the "confident-looking screen that is lying" DESIGN.md calls the worst outcome this product can produce.

**Fix.** Two parts, both reusing machinery that exists:
- After each write in `host.ts`/`dispatch.ts`, re-read via the existing `deps.load()` and compare the decoded target before toasting. Announce "Schedule saved" only on match; otherwise "Saved, but the controller reports something different — review it."
- Add a visibility-gated `setInterval(refresh, 4000)` in `mountDashboard` (UX-SPEC §11: 4s while visible, pause on `document.hidden`, back off 4→8→16→30s on failure). Track `lastSuccessTs`; render a header freshness line; set a `stale` flag after 3 missed polls that disables every `[data-action]` and submit.

**Watch out:** `host.ts:84-85` probes `location.origin` for the companion on *every* refresh. With a 4s poll that's a wasted round-trip per tick — hoist it.

### P0-2 — Safety inversions: valves open unguarded, rain delay self-cancels, programs default on

**Evidence.**
- `dispatch.ts:61-66` — `program-run` calls `api.runProgramNow(p)` with **zero** confirmation, from a button rendered on every card (`programs-view.ts:32`).
- `dispatch.ts:37` — `await api.setRainDelayHours( Number.isFinite(hours) && hours > 0 ? hours : 0 )`. Non-numeric input → `NaN` → **0 → cancels the rain delay**, then toasts "Rain delay cancelled." UX-SPEC §6.2 names this exact defect: *"Invalid input never maps to cancellation."* **The correct guard already exists 17 lines below** — `station-start` (`:54`) does `if (!Number.isFinite(mins) || mins <= 0) return null;`. Same file, two behaviors.
- `program-edit.ts:55` — `checkboxField("enabled", "Enabled", true)`. New programs default **on**, contra PRODUCT.md and UX-SPEC §7.2 ("New programs default to Save disabled").
- The confirmations that exist are `ctx.confirm("Delete this program?")` (`:75`) and `ctx.confirm("Reboot the controller now?")` (`:44`) — no target name, no consequence, and native `confirm()` focuses **OK**, inverting UX-SPEC §7.4's safe default.

**Why it's P0.** "Safe by default, destructive by consent" is design principle #3. Today the most destructive action (open valves) is the least guarded, and the safest action (pause watering) silently flips to its opposite.

**Fix.** Flip the `enabled` default to `false`. In `dispatch.ts:34-38`, parse first and bail on non-finite/negative — never map invalid → 0. Replace `ctx.prompt`/`ctx.confirm` with one native `<dialog>` (DESIGN.md sanctions it; `--shadow-3` is already reserved for exactly this) taking `{title, consequence, confirmLabel, danger}` and autofocusing Cancel. Gate `program-run` behind it using the copy UX-SPEC §7.4 already wrote: *"Run Front Lawn now? Valves may open for about 18 minutes, even though normal scheduling is off."*

**Note:** `ActionContext` (`dispatch.ts:11-14`) already injects `prompt`/`confirm` as a seam, so swapping the implementation to a `<dialog>` is a host-side change — `dispatch.ts` stays testable and the existing tests keep their injection point. But `prompt`'s `string | null` return can't express an inline validation error; widen the interface when you do this.

### P1-1 — Home is the firmware dashboard PRODUCT.md was written to prevent

**Evidence.** `dashboard.ts:71` routes the default tab to `renderControllerStatus` from `../spike/status-view` — a file whose own header says the UI framework choice is "a later step." It renders nine equal-weight rows including `Firmware 2.2.1 (0)+`, `Sunrise / Sunset`, `Cloud (OTC) status 1`, `Active stations 0` (`spike/status-view.ts:54-68`), plus **Reboot** (`:78`). Nowhere on this screen is *what will water and when* — the product's question #1.

**Why it matters.** PRODUCT.md lists "firmware/engineer dashboards… dense diagnostic tables as the default screen" as an anti-reference. UX-SPEC §5.1 says don't show firmware version/IP/OTC in the primary header; §6.2 says remove Reboot from Home. A homeowner opening this app cannot answer the question they opened it to answer.

**Fix.** Rebuild as UX-SPEC §6.1's five-block hierarchy: active watering (or "Nothing is watering now") → **next estimated watering** → weather decision → controller state → quick actions. Move `Firmware`, `Sunrise/Sunset`, `Cloud (OTC)`, `MAC`, `External IP` to Settings → System → Diagnostics — where `diagnostics-view.ts` **already renders all of them, better**. Then delete `spike/status-view.ts`.

**Note:** despite the directory name, `spike/status-view.ts` is production — `dashboard.ts:10` imports it. `spike/` is not dead code.

### P1-2 — No schedule edit flow; Diagnostics is top-level in a 7-tab bar

**Evidence.** `programs-view.ts:31-35` offers Run now / Enable / Delete — no Edit. `program-edit.ts:51` is hardcoded `<h2>New Program</h2>` and `host.ts:112` always calls `submitProgram(-1, …)` (create). To change a start time from 6:00 to 6:30, a user must delete the program and rebuild every duration by hand. No Copy. No conflict detection — UX-SPEC §7.3's fresh `/jp` re-read before save is absent, and `host.ts:92` passes a `data.jp` captured at the last refresh, which (with no polling) can be arbitrarily old. Two-tab editing silently clobbers.

`DASHBOARD_TABS` (`dashboard.ts:22`) is `[Status, Stations, Programs, Weather, Log, Diagnostics, Settings]` — 7 entries, 8 with History, against UX-SPEC §4.2's 5 + More. Diagnostics top-level is flatly banned by DESIGN.md. Vocabulary is still Stations/Programs/Log rather than Zones/Schedule/Activity (§4.1).

**Fix.** Add `actionButton("program-edit", "Edit", {pid})` as the first action in `programs-view.ts`; have `renderProgramEditor` accept an optional `ProgramView` to prefill and pass a real `pid` to `submitProgram`. Retitle tabs to Home/Schedule/Zones/Weather/Activity/More; fold Settings + Diagnostics under More (Diagnostics becomes a sixth `SETTINGS_SECTIONS` entry in `settings/index.ts:13`, reusing `renderDiagnostics` untouched). Make `nav.tabs` a fixed bottom bar under `@media (max-width: 700px)` with `env(safe-area-inset-bottom)` — `--tap` and the safe-area idiom already exist in the system.

**Watch out:** the toast is `position: fixed; bottom: calc(var(--space-5) + env(safe-area-inset-bottom))` and **will collide with the bottom nav** (UX-SPEC §17: "Bottom navigation… does not cover sticky wizard controls or toasts"). Handle both together.

### P2 — The program editor is one 27-control scroll where the spec asked for four steps

**Evidence.** `program-edit.ts:51-81` renders name + 2 checkboxes + 3 selects + 7 weekday checkboxes + 4 start-time **text** fields + N durations + 3 date fields in a single flat form. No review step, no validation gating submit, no total run time, no next-run preview. `host.ts:54-61`'s `[data-when]` conditional fieldsets are real progressive disclosure and the only thing keeping this under 30 controls.

`grep '<input type="time"\|<input type="date"\|<dialog' www/src` → **0 hits.** `program-edit.ts:49` asks a homeowner in sunlight to hand-type `HH:MM` into a text field; `:66,:77-78` ask for `YYYY-MM-DD` the same way. DESIGN.md mandates native inputs.

**Fix.** Two independent wins: (a) swap `textField` → a `timeField`/`dateField` emitting native `<input type="time">`/`<input type="date">` — the existing `parseClock`/`parseDate` already accept exactly the values those inputs produce, so this is a renderer change with **zero mapper changes**; (b) add UX-SPEC §7.2's Step-4 Review panel above submit — plain-English sentence, zones + durations, base total, next three **Estimated** occurrences. That panel is the natural home for P0-1's readback and P0-2's save-disabled confirmation.

### Minor — worth folding into whatever you touch nearby

- **12 orphan CSS classes** are emitted by views with no rule in any shipped stylesheet: `status`/`status-*` (`diagnostics-view.ts:25`), `health-summary`, `spark`, `spark-wrap`, `wls`, `weather-source`, `tab-label`, `tab-content`, `settings-content`, `help-icon`, `empty-msg`, `gauge-pct`. Most are harmless hooks — but **`.status-*` is meaning-bearing and silently inert**: `<span class="status status-warn">` matches neither `table.status` nor any `status-*` rule, so "Disabled" and "Enabled" render identically. The text saves it from a 1.4.1 failure; the level is dead markup. Either style them or drop them.
- **`#app h3` has no rule**, so the UA default (≈18.7px/700) renders **larger than `#app h2`** (18px/600). h3 outranks h2 in `weather-view.ts`, `diagnostics-view.ts`, `history-view.ts`. `article.program h3` is styled, so program cards escaped it; nothing else did. One rule in `system.css` fixes all of them.
- **`settings/weather.ts:37`** renders the API key as plaintext `<input type="text">`, no Reveal/Clear. `buildWeatherOptions` (`:52`) writes `wto.key = v.key` on **any** string including `""` — an empty submit **wipes the stored key**. UX-SPEC §8.4: "blank unchanged values do not overwrite stored keys."
- **`settings/network.ts`** sends octets through `ipOctets()` with no validation. UX-SPEC §9.3's "invalid octets/ports never coerce" and the old→new confirmation are both absent. Changing the IP silently orphans the app.
- **`host.ts:66`** does `mount.innerHTML = …` on every paint; focus is restored **only for tabs** (`:65,:72`). Save a settings form and focus is annihilated to `<body>`. A11y-relevant, and it gets worse once polling lands — don't repaint on a poll tick that changed nothing.
- **`helpTip`** (`help.ts:28`) is `role="img"` + `tabindex="0"`, so every Home row header is a focus stop announced as an image — 5 stops before reaching a control. `role="button"` + `aria-expanded` matches the actual behavior.
- **`logs-view.ts:30`** labels the column "When (UTC)" with a tip explaining timestamps aren't local. That's the honesty principle working — but `api/time.ts` already exists and `diagnostics-view.ts:29-33` uses it correctly. Honesty is standing in for the fix.
- **`programs-view.ts:25`**: `esc(p.days) + (p.oddEven !== "none" ? "" : "")` — a ternary returning `""` either way. Dead code where the odd/even restriction should surface; the badge row doesn't show it either, so a user cannot see a program is odd-days-only.
- **`esc()`** (`help.ts:17`) doesn't escape `'`. Every attribute in the codebase uses double quotes so it's safe today, but `actionButton`'s `data-${k}="${esc(String(v))}"` (`controls.ts:12`) is one refactor from a hole.
- **`app/index.html`** ships `<title>OpenSprinkler (next)</title>` — a build codename — and `<div id="app">Loading…</div>` has no `role="status"`.
- **Sunlight/muted violations** of DESIGN.md's Sunlight Floor Rule ("Slate Muted is for labels the eye skips, never for the answer the user came for"): remaining run time is `class="muted"` (`stations-view.ts:19`), log timestamps are `<td class="muted">` (`logs-view.ts:21`), relative times (`diagnostics-view.ts:32`), `.error-detail` (`system.css:200`). `--muted` on `--card` measures **5.98:1** — passes AA, but these are the answers.

## 5. Working agreements for whoever picks this up

- **Run the detector before and after.** `node .claude/skills/impeccable/scripts/detect.mjs --json app/index.html www/src` — currently **exit 0, clean**. Keep it that way.
- **Watch the gzip baseline.** 3319 bytes for `dist/assets/app.css`. UX-SPEC §14: >10% unexplained regression fails.
- **Tests are the safety net.** `npx vitest run` → 159 passing, covering contract, seam, decoders/encoders, views, dispatcher, settings mappers, a11y, and XSS. The dispatcher and settings tests will catch most P0 regressions.
- **Don't add a dependency.** Not a date picker, not a modal library, not a framework. `<dialog>`, `<input type="time">`, and `<input type="date">` cover every gap in the backlog above.
- **Tokens are the contract.** Add one only when it appears in 2+ shipped components (UX-SPEC §14); otherwise compose. New color? It goes in `tokens.css` *and* DESIGN.md's frontmatter, or the detector flags it.
- **A live browser pass is still owed.** This critique had no browser automation. Nobody has verified the 320px wrapped nav, real focus order, or render-time contrast against actual pixels. Do that before trusting any "responsive is fine" claim.
