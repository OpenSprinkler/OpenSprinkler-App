## Anti-Patterns Verdict

**Does this look AI-generated? No — and that's not the problem.**

**LLM assessment**: Zero hits across every cross-register ban. No gradient text, no glassmorphism, no side-stripe borders (`system.css:130` uses a full 1px hairline + `--accent-soft` ground, exactly as DESIGN.md specifies), no hero-metric tile, no identical card grid, no uppercase eyebrows, no 01/02/03 numbering. They would flinch at the **screens**. ## Overall Impression

The design system is three phases ahead of the product it dresses. `tokens.css` derives accent variants via `color-mix` so dark mode inherits from one redefinition; `system.css` gives a 13px glyph a 44px hit area without consuming 44px of layout. That is genuinely mature work. Meanwhile the rain delay is a `window.prompt` that cancels itself on a typo, and `Run now` opens valves with no confirmation at all.

The single biggest opportunity: **the app's founding promise is unimplemented in every mutation path.** PRODUCT.md says "no mutation ever claims success it did not verify." Zero mutations verify. Every write toasts success the instant HTTP resolves, and because nothing polls, the user gets a toast saying it worked next to a screen that doesn't change. That's the exact "confident-looking screen that is lying" the doctrine calls the worst outcome this product can produce.

## What's Working

1. **`helpTip` is a genuinely correct, genuinely hard component** (`help.ts:26-31` + `system.css:86-98`). It's the accessible name *and* a visible bubble on hover *and* `:focus-visible` *and* `:focus` — that last one is what makes it work on iOS tap, where `:focus-visible` alone silently fails. Most teams ship a `title` attribute and call it accessible. It works because it treats "explain on demand" as a first-class control, which is exactly the progressive-disclosure lever this product needs everywhere else.

2. **The token layer is disciplined in the way that survives a theme flip.** Derived `--accent-weak/soft/strong` via `color-mix` (`tokens.css:33-35`), so one redefinition carries the family. Simultaneously `.badge.on`/`.toast.err` **hardcode** their fills. That inversion is the right call and an unusually mature one: derived tokens for chrome, theme-immune constants for meaning-bearing marks, so a running zone can't change color when the OS flips to dark.

3. **Redundant coding is real, not claimed.** `dotOff()` is a ring **with a slash through it** — shape, not just a gray fill. The active tab is color **+** weight **+** underline. `stations-view.ts:18-19` pairs the pulsing dot with the word "On" *and* the remaining time. "Color is never the only signal" is usually a line in a doc; here it's in the SVG path data.

## Priority Issues

### [P0] Every mutation claims success it never verified, and nothing ever refreshes

**Why it matters**: This is the founding promise (PRODUCT.md: "no mutation ever claims success it did not verify"). A homeowner taps Stop all with water running, gets "All stations stopped.", sees an unchanged screen, and cannot tell whether the request landed. `host.ts` calls `refresh()` once at mount; grep for `setInterval` / `visibilitychange` / `navigator.onLine` across `www/src` returns **0**. So there is no Stale state, no Offline state, no "Last updated", no write-disabling when unreachable — the whole UX-SPEC §10 state table and §11 freshness contract are missing.

**Fix**: (a) After each write in `host.ts` / `dispatch.ts`, call the existing `deps.load()` and compare the decoded target before toasting — announce "Schedule saved" only on match, else "Saved, but the controller reports something different — review it." (b) Add a visibility-gated `setInterval(refresh, 4000)` in `mountDashboard`, track `lastSuccessTs`, render a header freshness line, and set a `stale` flag that disables every `[data-action]` and submit. Both reuse machinery that already exists.

**Suggested command**: `/impeccable harden`

### [P0] Run now opens valves with no confirmation; rain delay cancels itself on a typo; new programs save enabled

**Why it matters**: "Safe by default, destructive by consent" is design principle #3. Today the most destructive action (open valves) is the *least* guarded, and the safest action (pause watering) silently flips to its opposite.
- `dispatch.ts:61-66` — `program-run` calls `runProgramNow(p)` with **zero** confirmation, from a button on every program card.
- `dispatch.ts:37` — `setRainDelayHours(Number.isFinite(hours) && hours > 0 ? hours : 0)`. Fat-finger a letter and the app **cancels the rain delay** and toasts "Rain delay cancelled." UX-SPEC §6.2 names this exact bug: *"Invalid input never maps to cancellation."* The correct guard already exists **17 lines below** in the same file — `station-start` (`:54`) returns null on non-finite input. Two behaviors, one file.
- `program-edit.ts:55` — `checkboxField("enabled", "Enabled", true)`. New programs default **on**, contra PRODUCT.md and UX-SPEC §7.2.

**Fix**: Flip the `enabled` default to `false`. In `dispatch.ts:34-38`, parse first and bail on non-finite/negative — never map invalid → 0. Replace `ctx.prompt`/`ctx.confirm` with one native `<dialog>` (DESIGN.md already sanctions it; `--shadow-3` is already reserved for it) taking `{title, consequence, confirmLabel, danger}` and autofocusing Cancel. Gate `program-run` behind it with the copy the spec already wrote: *"Run Front Lawn now? Valves may open for about 18 minutes."*

**Suggested command**: `/impeccable harden`

### [P1] Home is the firmware dashboard PRODUCT.md was written to prevent

**Why it matters**: `dashboard.ts:71` routes the default tab to `renderControllerStatus` from `../spike/status-view` — a file whose own header describes it as a seam spike. It renders nine equal-weight rows (`Firmware`, `Sunrise / Sunset`, `Cloud (OTC) status 1`, `Active stations 0`) plus **Reboot**. Nowhere on this screen is *what will water and when* — the product's question #1. A homeowner opening this app cannot answer the question they opened it to answer. UX-SPEC §5.1 explicitly says don't show firmware version/IP/OTC in the primary header; §6.2 says remove Reboot from Home.

**Fix**: Rewrite as UX-SPEC §6.1's five-block hierarchy: active watering (or "Nothing is watering now") → **next estimated watering** → weather decision → controller state → quick actions. Move `Firmware`, `Sunrise/Sunset`, `Cloud (OTC)`, `MAC`, `External IP` to Settings → System → Diagnostics, where `diagnostics-view.ts` **already renders all of them, better**. Then delete `spike/status-view.ts`.

**Suggested command**: `/impeccable shape` (Home is a redesign, not a polish)

### [P1] You cannot edit a schedule, and Diagnostics is a top-level tab

**Why it matters**: "Move the back lawn to 6am" is one of four named jobs in PRODUCT.md, and it is impossible without data loss — `programs-view.ts:31-35` offers only Run now / Enable / Delete, so changing a start time means deleting the program and rebuilding every duration by hand. No Copy, and no conflict detection (§7.3's `/jp` re-read is absent), so two-tab editing silently clobbers. Meanwhile `DASHBOARD_TABS` is 7 entries (8 with History) against the spec's 5 + More, with Diagnostics top-level — which DESIGN.md flatly bans. At 320px those tabs wrap into 3-4 rows of chrome above any content, at the top of the screen, in the phone-at-the-valve-box case.

**Fix**: Add `Edit` as the first action in `programs-view.ts`; have `renderProgramEditor` accept an optional `ProgramView` to prefill and pass a real `pid` to `submitProgram`. Retitle tabs to Home/Schedule/Zones/Weather/Activity/More, fold Settings + Diagnostics under More (Diagnostics becomes a sixth `SETTINGS_SECTIONS` entry, reusing `renderDiagnostics` untouched), and make `nav.tabs` a fixed bottom bar under `@media (max-width: 700px)` with `env(safe-area-inset-bottom)`.

**Suggested command**: `/impeccable layout`

### [P2] The program editor is one 27-control scroll where the spec asked for four steps

**Why it matters**: This is the product's primary task, performed on a phone. `program-edit.ts:51-81` renders name + 2 checkboxes + 3 selects + 7 weekday checkboxes + 4 start-time **text** fields + N durations + 3 date fields in one flat form, no review, no validation, no total run time. And `textField("t_0", "Start time 1", …, {placeholder: "HH:MM (blank = unused)"})` asks a homeowner in sunlight to hand-type a 24-hour clock string while `<input type="time">` — mandated by DESIGN.md, free, native, locale-formatted, already parseable by the existing `parseClock` — sits unused.

**Fix**: (a) Swap `textField` → `timeField`/`dateField` emitting native inputs; `parseClock`/`parseDate` already accept exactly the `HH:MM`/`YYYY-MM-DD` values those produce, so it's a renderer change with zero mapper changes. (b) Add a Step-4 Review panel above submit — plain-English sentence, zones + durations, base total, next three **Estimated** occurrences. That panel is also the natural home for P0's readback.

**Suggested command**: `/impeccable craft` (the four-step flow is a build, not a tweak)

## Minor Observations

- **12 orphan CSS classes** are emitted by views with no rule in any shipped stylesheet: `status`/`status-*`, `health-summary`, `spark`, `spark-wrap`, `wls`, `weather-source`, `tab-label`, `tab-content`, `settings-content`, `help-icon`, `empty-msg`, `gauge-pct`. Most are harmless hooks; **`.status-*` is meaning-bearing and silently inert.**
- `#app h3` has no rule anywhere, so UA default (≈18.7px/700) renders **larger** than `#app h2` (18px/600). h3 outranks h2 in `weather-view.ts`, `diagnostics-view.ts`, `history-view.ts`. `article.program h3` is styled, so program cards escaped it; nothing else did.
- `settings/weather.ts:37` renders the API key as plaintext `<input type="text">`, no Reveal/Clear. `buildWeatherOptions` writes `wto.key = v.key` on **any** string including `""` — an empty submit **wipes the stored key**, exactly what UX-SPEC §8.4 forbids.
- `settings/network.ts` sends octets with no validation — §9.3's "invalid octets never coerce" and the old→new confirmation are both absent. Changing the IP silently orphans the app.
- `logs-view.ts:30` labels the column "When (UTC)" with a tip explaining timestamps aren't local. Honest — genuinely commendable — but `api/time.ts` already exists and `diagnostics-view.ts` uses it correctly. Honesty is standing in for the fix.
- `programs-view.ts:25`: `esc(p.days) + (p.oddEven !== "none" ? "" : "")` — a ternary returning `""` either way. Dead code where the odd/even restriction should surface; the badge row doesn't show it either, so a user cannot see that a program is odd-days-only.
- `esc()` (`help.ts:17`) doesn't escape `'`. Every attribute uses double quotes so it's safe today, but `actionButton`'s `data-${k}="${esc(String(v))}"` is one refactor from a hole.
- `host.ts:84-85` probes `location.origin` for the companion on **every** refresh. With P0's 4s polling added, that's a wasted round-trip every tick.
- `app/index.html` ships `<title>OpenSprinkler (next)</title>` — a build codename — and `<div id="app">Loading…</div>` has no `role="status"`.
- The toast is `position: fixed; bottom: calc(--space-5 + safe-area)` and will collide with the bottom nav the spec requires (§17: "Bottom navigation… does not cover sticky wizard controls or toasts").
